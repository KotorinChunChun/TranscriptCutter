# v4.1.0 実装計画・報告書

## 設計

- 既存protocolVersion=3、既定loopback、認証、保存データと既存API応答を保持。新機能は任意パラメーターと追加フィールド・APIで提供する。移行先PCのIPや認証値は固定しない。
- フェーズ1：中止・完了の状態遷移を直列化し、待機中中止の管理情報を確実に解放する。例外でワーカーが黙って終了しないようにする。データを除いた独立Gitリポジトリを初期化し、検証後コミットする。
- フェーズ2：file/realtimeの独立実行枠を用意。従来要求はfile、clientId/workloadは任意。CPUの短区間処理を長いファイルと分離。GPU・autoはGPU利用の可能性があるため共通排他でメモリ過剰確保を避ける。Whisperは枠ごとに最大1プロセスを再利用し、モデル変更・中止・失敗・アイドル期限で破棄する。speech.cpp/APIは従来プロセス単位を維持する。
- フェーズ3：SQLによる履歴ページング・clientId/workload分類、容量表示、稼働API、待ち時間・処理時間・モデル読み込みの計測とWeb管理表示。既存GET /api/jobsは互換、limit指定時はページング。元データは自動削除しない。容量整理は完了ジョブのメディアだけを明示確認の上で削除し、字幕・編集・IDを保持する方式とする。
- フェーズ4：別PC向けWindows x64バイナリ（Python不要、Whisper CPUランタイムを含む、モデル・speech.cpp・FFmpegは別配置）とソースZIP、SHA256、ライセンスを作成。凍結EXEのワーカー・能力検出の再実行を専用引数で実装する。別PC起動と認証の手順を整備する。
- 指定チャネルへ、clientId/workloadの追加と将来の別PCサーバー接続に関する互換対応を依頼する。既存クライアントの既定接続先は変えない。
- GitHubの対象リポジトリ・公開範囲はユーザーへ確認中。ローカル成果物と検証を先に完了し、指定後にソース公開・タグ・Release assetsを順に行う。認証値、録音、モデル、PC固有台帳は公開しない。

## 検証

- 既存Python/JavaScript試験と回帰試験。待機中/実行中の中止、完了と中止の競合、レーン分離、エラー後継続、履歴ページング、認証と容量整理のデータ保持。
- 業務データを使わず別ポート・専用データで合成音声を実認識。モデル再利用、別レーン進行、処理時間、CPU、Whisper話者識別と既存クライアント互換を区別する。
- 作成EXEは展開先でPython依存なしの起動、モデル一覧、実認識、再利用、中止、認証モードを確認する。移行先PCそのものとGPUの受入は未確認として記録する。

- GPU非対応時のautoは受付時の能力でCPUへ確定し、利用者のdevice=autoは保持。GPU候補のみ保守的に排他とする。
