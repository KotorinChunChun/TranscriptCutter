# v0.1.14 並列実行 実装計画・報告

## 設計（実装前）

- 既存のfile/realtime APIを維持し、単一ディスパッチャーで最大10実行ワーカーへ割り当てる。枠0/1は既存の手動常駐操作との互換用、その他は共用とする。処理範囲制限は枠番号ではなくworkloadで判定する。
- 各要求が使用するワーカーを占有し、標準入出力・取消トークン・字幕・所有プロセスを共有しない。既存のGPU→CPU再試行を維持し、そのCPU用RAMも事前予約する。
- 並列数、リアルタイム予約枠、RAM/VRAM予算、GPU並列数を設定する。最大10件、RT予約2件を既定とする。予算は同一モデルの複製・話者分離・前処理を含む保守的な見積り。OSのRAM空きも確認し、GPU容量不明時は無制限扱いしない。
- 実行中と常駐中をともに計上する。余分な自動ワーカーは終了確認後に解放。手動常駐ワーカーは予約費用を保持し、未使用キャッシュの置換は実行中のモデルへ影響させない。GPUの全体排他と他枠キャッシュの無条件破棄を除去する。
- RT優先、同じworkload内ではclientIdを交替して配分する。clientIdはアプリ分類であって認証ではない。ファイル用にも最低1実行枠を残し、割込みは行わない。RTの即時開始は資源や実行中処理により保証しない。
- 予算は推定に基づく開始制御であり、OSによるメモリ上限強制ではない。未知のモデルは実行せず待機。GPU容量は検出または明示設定し、実GPUの同時推論受入と合成検証を区別する。
- UI設定は既存の設定ダイアログへ追加。変更は全ジョブ停止中だけ許可し、不正値や競合は拒否する。既存設定JSONの未知項目を保持し、保存成功後に反映する。
- 自動ワーカー数/資源待ち/モデル別件数をAPIへ追加し、時間計測の既存意味を維持する。必須ファイル保持チェックを使い、合成HTTP並列試験と実小型モデルの隔離試験を実施する。

## 第1フェーズ結果

- 単一スケジューラーと最大10ワーカーを実装。同じモデルも独立プロセスへ割り当て、実行/常駐のRAM・VRAM見積りとGPU並列数で開始を制御する。GPU排他と他枠の無条件破棄を除去。
- RT予約枠に加え、ファイル処理は同じ比率の資源予算を残す。clientIdを交替、同一client内は投入順。大きなモデルの資源待ちは小型モデルの実行を妨げない。
- 自動ロードはジョブ終了時に終了確認して解放。手動常駐は維持。終了未確認は枠と予算を隔離して再利用しない。
- Whisper/native CPUスレッドは未指定時に並列数で分配（1〜4）。RT30秒制限をworkloadで判定。GPU失敗時のCPU再試行と取消・時間計測を保持。
- `cargo test --locked -j 4`: 69成功。HTTP合成試験で8 file + 2 realtimeの同時開始、同一/異なるWhisperモデル、CPU/GPU合成混在、11件目待機、1件のみ取消、各要求固有の字幕、RT優先、RAM待機後の再開、file75秒/RT30秒制限を確認。GPUは合成で実機受入ではない。
- `cargo clippy --locked --all-targets -j 4 -- -D warnings` 成功。`cargo fmt --all` 適用。
- RAM空き判定は、まだ実メモリへ反映されていない同時ロード予約も含め保守的に判定する（既に使用中の一部を二重計上し得る）。物理メモリ不足時に10件を強制実行しない。
