# 共通HTTPS証明書の運用規程

2026-10-15ユーザー指定。C:/develop配下から、このPCで公開するWebサービスに適用する。管理主体はDevServer。アプリ署名用exampleDev-Testとは分離する。

## 正式な参照先

| 用途 | 参照 |
|---|---|
| 共通サーバー証明書 | C:/AI/Certificates/example-Dev-Server.crt |
| サーバー秘密鍵 | C:/AI/Certificates/example-Dev-Server.key |
| サーバー証明書と発行元のPEMチェーン | C:/AI/Certificates/example-Dev-Server-chain.pem |
| 利用PCへ配布する認証局公開証明書 | C:/AI/Certificates/example-Dev-RootCA.cer（DER）または.crt（PEM） |
| 実機の期限・SAN・拇印・公開ファイルSHA256 | C:/AI/Certificates/example-Dev-Server.json（Git対象外） |
| 認証局の秘密鍵 | Cert:/LocalMachine/My。manifestのroot_thumbprintで特定。非エクスポート可能 |

サーバー証明書の名前はexample-Dev-Server、発行元はexample-Dev-RootCA。サービスは発行元の秘密鍵を使用しない。認証局をWindowsの「個人」に格納することと「信頼されたルート」に登録することは別操作である。

## 適用ルール

- 新規・変更時のHTTPSは原則この共通証明書を参照する。アプリごとの自己署名証明書生成を通常起動に入れない。既存サービスは対象・バックアップ・停止起動方法を確認して段階的に移行する。
- ポートは証明書の対象名に含まれない。同じ証明書のSANに登録されたIP・DNS名に限り、複数ポートで共用できる。IP・ホスト名の追加はSANの確認と再発行が必要で、ファイル名を変えても対象は増えない。実際のSANはmanifestを読む。
- TLS1.2以上、既存のEntra認証・Host/Origin検査・社内LAN制限・固定ポート・内部loopbackを維持する。TLS証明書の共用は、Entraアプリ登録・クライアント認証証明書・利用権限の共用を意味しない。
- 各サービスは正本ファイルを絶対パスで参照する。形式の都合で派生PFX等が必要ならDevServer管理で保護した実行環境用派生物を作り、元証明書との一致・更新手順を記録する。アプリの独断で再発行しない。
- 秘密鍵のACLは管理者・SYSTEM・必要なサービス実行者だけ。既定生成時は管理者・SYSTEM・作成本人のみ。一般ユーザー全員への読取・変更権限を付けない。サービスごとの読取追加は実行者を確認して明示的に行う。
- PEM秘密鍵は無人サービス用のためファイルACLで保護する。共有フォルダー、Git、Web配布、チャット、ログへ秘密鍵・PFX・パスワードを出さない。公開証明書だけを利用PCへ配布する。
- 各利用PCは拇印を確認してRootCA公開証明書を「信頼されたルート証明機関」へ登録する。登録は管理者の承認された配布か利用者本人が行う。ブラウザーの証明書検証を無効化する運用は採用しない。
- 証明書を共通パスへ置くだけでは各サーバーに適用されない。設定変更・TLS再読込または公式再起動が必要。設定済み、カスタムCAでの接続成功、Windows信頼登録済み、実ブラウザー確認済みを分けて報告する。

## 作成・更新・復旧

初回生成はscripts/New-exampleDevServerCertificate.ps1を管理者pwshで実行する。既存の保存先・同名CAがあれば停止し、上書きしない。信頼登録・サービス切替は自動実行しない。

CAは10年、サーバー証明書は1年。サーバー証明書は期限90日前に確認し、同じCAで更新する計画を立てる。更新前に全参照サービス・所有者・再読込方法を確認し、旧ファイルと設定を保護バックアップする。新しい鍵ペア・証明書を別パスで検証してから切り替え、各サービスを確認する。既存CAを作り直す生成スクリプトの再実行で更新しない。

CA秘密鍵は非エクスポート可能であり、CERのバックアップだけでは再発行能力を復元できない。Windows鍵ストアを含む保護されたシステムバックアップが必要。鍵を失った場合は新CAの配布・各PCの信頼再登録が必要となる。サーバー秘密鍵と設定のバックアップも暗号化・アクセス制限付きで管理する。

漏えい時は共用する全サービスが影響範囲。共有鍵を交換し、CA秘密鍵の侵害ならCAも交換して旧信頼を除去する。共通ファイルを変更する権限は証明書管理担当に限定する。

## 既存サービス移行

1. PUBLISHING-POLICY.md、各AGENTS、DevServer台帳から対象環境・入口・実行者・公式起動停止を照合する。
2. 現設定・既存証明書の公開情報・バックアップ・復旧方法を記録する。秘密値は出力しない。
3. SAN、期限、Server Authentication、公開鍵と秘密鍵、必要なACLを確認して共通参照へ変更する。
4. 対象だけを公式管理入口で再読込・再起動し、実際の配信証明書とmanifestの一致を検証する。
5. 信頼設定済みのPCで警告なしのHTTPSと既存サインイン・代表機能を確認し、未実施は残す。

本番サービスの切替・再起動は対象と操作を明示したユーザー指示が必要。この規程は既存全サービスの一括変更を許可しない。
